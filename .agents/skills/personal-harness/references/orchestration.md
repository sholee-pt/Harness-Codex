# 작업 분할 기준

## 단일 에이전트가 적합한 경우

- 변경 지점이 한두 파일에 집중되어 있습니다.
- 조사 결과가 바로 다음 구현 단계의 입력이 됩니다.
- 여러 작업자가 같은 코드를 수정할 가능성이 높습니다.
- 검증 비용보다 조정 비용이 더 큽니다.

## 병렬 하위 에이전트가 적합한 경우

- 보안, 테스트, 성능처럼 서로 다른 관점의 읽기 중심 검토가 필요합니다.
- 여러 패키지나 모듈이 명확히 분리되어 있습니다.
- 각 작업이 다른 작업의 중간 결과 없이 진행될 수 있습니다.
- 각 결과를 주 에이전트가 객관적인 기준으로 비교·통합할 수 있습니다.

## 역할 설계 원칙

- 역할 이름보다 산출물을 먼저 정합니다.
- 역할마다 하나의 주요 질문만 부여합니다.
- 조사 역할은 파일을 수정하지 않습니다.
- 구현 역할의 파일 소유권은 겹치지 않게 합니다.
- 최종 판단과 사용자 보고는 주 에이전트가 담당합니다.

## 중단 조건

- 요구사항 충돌, 권한 부족, 파괴적 변경 필요성이 발견되면 해당 작업을 중단하고 보고합니다.
- 같은 실패를 반복하지 말고 원인과 대안을 확인합니다.
- 근거가 없는 추정으로 검토 결과나 테스트 성공을 만들지 않습니다.
